# 2D and 3D mesh / animation demonstrations

The repository testing application includes `geometry/mesh-animation-demo`, using the
installed `gffx.dashboard` image and WebGPU mesh panels. This is a finite gallery, not
the planned gffx animation operator API and not a graphics conformance claim.

From the repository with the intended installed gffx wheel:

```powershell
python -m tools.testing_dashboard.mesh_animation_demo --address http://127.0.0.1:8791 --run mesh-animation-UNIQUE
```

The producer uses only Python's standard library plus gffx.dashboard. It exits after:

- A planar mesh: 81 vertices, 128 triangles, a fixed front-view wireframe image and an
  orbitable view of the same XY plane (Z=0).
- A spatial ring mesh: 192 vertices and 384 triangles, with vertex colours.
- A 24-frame planar-deformation image clip and a 24-frame breathing/bending mesh clip.
- Plain-language explanations of coordinates, topology, controls and limitations.

Playback starts paused. Play runs once to the last frame; pressing Play at the end starts
again. Previous/next and the shared frame slider inspect individual frames. Requested
rates are 4, 8, 12, 24, 30 or 60 fps maximum; frame delivery can make actual playback slower. No next
frame request is scheduled until the preceding display request finishes. Pausing, hiding
the document, changing page or reconnecting disposes/stops playback rather than starting
an unattended loop. Pinned frame references remain static and have no autoplay controls.

Both finite queues explicitly use `recent_window=24, snapshot_every=1`, retaining the
complete short clip after a restart. This does not change general live-stream defaults
(100 recent updates / one snapshot per 1000 source steps). Images are 240x180 RGB; meshes
remain tiny. Existing server log, memory and browser cache quotas still apply; missing
frames must be reported, not silently substituted. No continuously running producer,
dataset, external model, new runtime dependency or background optimization is needed.

The planar image is an illustrative wireframe generated by this demo, not the production
rasterizer. Procedural vertex motion preserves connectivity; it is not skinning,
blendshapes, motion retargeting or evidence that M1's animation subproject is complete.

## Stanford bunny, Utah teapot and elastic ball

Two further permanent pages are `geometry/classic-meshes-demo` and
`simulation/elastic-ball-demo`. From a repository checkout with the bundled fixtures:

```powershell
python -m tools.testing_dashboard.classic_demo --address http://127.0.0.1:8791 --run classics-UNIQUE
```

This creates two separate finite execution records (`classics-UNIQUE` and
`classics-UNIQUE-ball`), because one demonstration page owns each execution. Both
finish; there is no background producer. Each page has its own readable explanation.

The bundled bunny (1,889 vertices / 3,851 triangles) and Utah teapot (1,568 vertices /
2,256 triangles) are offline developer fixtures, not runtime package assets. Read
[their attribution and terms](../tools/testing_dashboard/demo_assets/README.md) before
redistributing: the Stanford source has commercial-use restrictions; the teapot
derivation retains three.js's MIT notice. No three.js dependency is introduced.
The assets are excluded from wheels/source distributions; use a checkout for these demos.

The ball illustration integrates a 1 kg centroid from 2 m height with gravity
9.81 m/s², a unilateral 1,200 N/m contact spring, and 5 N·s/m damping. Semi-implicit
Euler uses 40 substeps per 1/60-second output frame. Its visible ellipsoid preserves
volume while squashing to stay above the rigid, wooden-coloured floor. This is not
a mesh dynamics solver, measured wood model, public gffx physics API, differentiable
simulation, or finite-element validation. Heights and total mechanical energies
are plotted separately; plot X is frame index, so simulation seconds = X / 60.

The ball and floor total 186 vertices / 308 triangles. There are 181 saved frames
(three seconds), with `recent_window=181, snapshot_every=1`, plus 61 samples per
scalar curve. These explicit finite-demo settings leave normal live retention and
all byte quotas unchanged. Every frame is retained; there is no interpolated fake
history. The ordinary browser cache still has its own bound.

Select **60 fps max** and press **Play** for intended real-time playback. The default
8 fps remains unchanged; lower targets give slow motion. Display/fetch elapsed time
is subtracted from the target interval, but requests stay serial: slow delivery
slows playback rather than creating a catch-up queue. No measured 60-fps guarantee
on a laptop, iPad, phone or remote connection is implied.

Tests compare free fall against its analytic trajectory, check rebound and energy
loss, bound the difference after halving the integration timestep, verify mesh
topology/floor separation, and reload clip endpoints after a server restart.

The 2026-09-07 gallery extension adds a grey rest-grid overlay to the planar clip,
fixed-scale displacement colors to the spatial clip, optional native normal/area
inspection on classic meshes, and impact seeking with four exact-frame ball energy
meters. Those four component curves have 181 samples each; the original two height
and total-energy curves retain 61 each. Missing exact scalar samples are labelled,
not invented. See [Visual demonstrations](DEMONSTRATION_SHOWCASE.md) for reproduction,
the lighting/camera studio and the distinction between illustrations and public APIs.
